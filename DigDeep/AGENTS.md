# DigDeep 작업 지침

- 제작/수정을 시작할 때 예상 소요 시간을 안내한다.
- 사용자가 명시적으로 요청하지 않으면 빌드하지 않는다. 자동 검증용 플레이어 빌드도 금지한다.
- 평소 검증은 유니티 컴파일과 에디터 측 테스트로 진행한다.
- 새 저장 및 데이터 초기화 후 최초 지급은 나무 곡괭이 하나다. 기존 정상 저장의 소유 곡괭이는 보존한다.
- 저장은 돈/광물/소유 곡괭이/강화 등 성장 정보만 포함한다. 현재 판의 지형/내구도/위치는 저장하지 않는다.
- 광물 확인 기록도 성장 정보로 저장한다. 최초 채굴 획득 시 확인하며, 판매 탭에는 확인한 광물만 표시하고 판매한다. 전량 판매 후에도 확인 기록을 보존한다.
- 상점은 구매/판매 탭을 사용한다. 광물 목록은 등록 정보로 생성하고 세로 스크롤하며, 수량/총액/판매 영역은 고정한다.
- 튜토리얼은 Dig!! → 탭 → 드래그 → 홀드 순서다. 첫 실제 게임 오버 후 인벤 → 상점 → 강화 설명을 진행한다. 재정비는 첫 판 종료로 계산하지 않는다. 거래 자체를 강제하지 않는다.
- 완료한 튜토리얼 단계만 저장하고 미완료 단계는 다음 접속에서 이어간다. 첫 구매 이후 소진된 곡괭이를 교체할 때 안내를 한 번 완료하도록 한다. 데이터 초기화는 모든 튜토리얼 기록도 초기화한다.
- 드롭 실패의 길 막힘/범위 초과 안내는 튜토리얼 완료 후에도 제공한다. 상하 이동은 시작 위치 기준 각각 2칸, 좌우 이동은 기존 규칙을 유지한다. 광물 획득 글자는 해당 광물 이미지의 색을 사용하고, 파편·섬광·글자는 고정된 개수를 재사용한다.
- 모든 곡괭이 머리 윤곽은 손잡이 중심선을 기준으로 좌우 대칭으로 만든다.
- 앞으로 추가하는 곡괭이도 Pickaxes-v3.png의 돌 곡괭이와 같은 머리/손잡이 비율, 손잡이 길이, 표시 크기로 만든다. 재질과 색으로 종류를 구분한다.
- 앞으로 이미지를 교체할 때 새 리소스의 적용과 표시를 확인한 뒤, 참조가 없고 향후 사용 계획이 없는 이전 이미지는 해당 .meta와 함께 삭제한다. 혼합 시트 등 아직 사용하는 이미지와 Unity 참조는 보존한다. 표시 각도처럼 기존 이미지로 처리할 수 있는 변경은 새 이미지 용량을 늘리지 않는다.
- 라인을 설명할 때 시작~끝 행과 포함하는 줄 수를 함께 표기한다. 1라인 2~10행(9줄), 2라인 11~25행(15줄), 3라인 26~45행(20줄), 4라인 46~65행(20줄).
- 철광석 이미지는 길쭉한 광맥 대신 돌 바탕에 여백을 남긴 각진 네모 덩어리로 만든다.
- 현재 구현 규칙은 Docs/MiningUpgrade-2026-10-13.md를 참고한다. 이전 문서보다 사용자 최신 결정이 우선한다.
- 최고 도달 행은 성장 정보로 자동 저장하며 재정비·게임 오버·재접속 시 유지한다. 현재 판의 깊이와 구분하고, 초기화 시 함께 지운다.
- 채굴 종료 결과에는 이번 판의 도달 깊이(행)만 표시한다. 돈·광물 내역과 추가 설명은 생략하고 다시 준비 버튼은 유지한다. 획득 재화와 저장은 정상 반영한다.
- 상점·인벤·강화 버튼은 80×50, Dig!!는 230×64다. 터치 영역과 튜토리얼 강조는 실제 버튼 RectTransform을 공유한다.
- 발표용 재화 버튼은 독립적인 PresentationTools 자식에 둔다. 삭제/비활성화해도 핵심 게임에 영향을 주지 않아야 한다. 지급은 대기 중에만 허용하고 튜토리얼 진행은 바꾸지 않는다.
- 버튼·기록·발표 도구의 적용 및 제거 방법은 Docs/UI-Records-2026-10-14.md를 참고한다.
- 제련은 강화/변환 탭으로 구성한다. 변환 레시피를 데이터로 등록하여 여러 광물을 지원하고, 현재는 석탄 1개를 에너지 0.1로 변환한다. 에너지는 0.1 단위 정수로 계산·저장하고 인벤에서 한 자리 소수로 표시한다.
- 다이아 곡괭이는 합금 다음 단계, 비용 500원+다이아몬드 20개+에너지 5, 내구도 110, 타격당 피해 3이다. 다이아 광물은 체력 30/판매 37원, 석유는 체력 30/판매 60원이다.
- 최신 4라인·제련 규칙과 저장 형식 7은 Docs/Refining-2026-10-20.md를 참고한다. 제작 요청만으로 웹 빌드/배포를 실행하지 않는다.

## 웹 빌드 요청 기본값
- 사용자가 '디그딥 빌드해줘'라고 요청하면 기본 대상은 Web(WebGL)이다.
- 사용자가 별도로 요청하지 않으면 Windows 실행 파일이나 테스트용 플레이어 빌드는 만들지 않는다.
- 앞으로 웹 빌드 요청은 WebGL 빌드 후 GitHub Pages 배포까지 포함한다. 사용자가 다른 범위를 지정하면 해당 요청을 따른다.
- GitHub Pages의 공개 HTTPS 주소에서 실행을 확인하고, 실행 방법·공개 접속 링크·해당 링크의 QR 코드를 함께 제공한다. 다른 PC나 모바일 및 다른 네트워크에서도 접속할 수 있어야 한다.
- 배포는 게임의 WebGL 결과 파일을 대상으로 한다. 저장소·인증·Pages 설정이 없거나 배포가 실패하면 필요한 사항을 구체적으로 알리고, 로컬/LAN 링크를 공개 배포 완료로 대신 제시하지 않는다.
- 사용자는 앞으로 빌드를 요청할 때 GitHub Pages 배포도 함께 수행하도록 승인했다. 같은 배포에 대한 일반 확인을 반복하지 않으며, 도구의 필수 권한 승인 절차는 따른다.
- 접속 링크는 실제 실행 또는 배포된 주소를 사용하고, 실행 가능 여부를 확인하지 않은 주소를 완료된 링크로 제시하지 않는다.
- 모듈 설치만 요청받은 경우에는 게임 빌드 또는 배포를 실행하지 않는다.


## GitHub Pages 배포 구성
- 저장소: sangbeen0912/DigDeep. 웹 배포 브랜치 gh-pages, 공개 주소 https://sangbeen0912.github.io/DigDeep/.
- 빌드 후 Tools/Deploy-GitHub-Pages.py publish로 웹 결과 파일을 배포한다. 재시도 시 기존 설정/원격 상태를 먼저 확인한다. 첫 설정 응답이 실패했지만 설정이 이미 적용된 경우 configure로 기록만 마무리할 수 있다.
- status로 Pages의 성공 상태와 Builds/PagesDeployment.json의 커밋이 일치하는지 확인하고, 공개 release.json과 실제 브라우저 실행·채굴·저장을 검증한다.
- 배포 결과는 Builds/PagesPublish, 공개 접속 QR은 Builds/DigDeep-QR.png, 실행 설명은 Builds/실행방법.md에 기록한다. 공개 QR을 로컬/LAN 주소로 바꾸지 않는다.
- 인증은 기존 Git Credential Manager를 사용하며 토큰을 출력하거나 파일·로그에 저장하지 않는다. 배포 브랜치는 정상적인 fast-forward push로 업데이트한다.
